### Added: `GET /api/me` (`functions/api/me.ts`, `functions/_lib/me-core.ts`)
- **What it does.** Reads the one sign-in cookie (`cbsess`: `HttpOnly`, `Secure`, `SameSite=Lax`, set on the console address only, never with a `Domain`). Signed in: `{ "signedIn": true, "name": "Raajat Agarwal", "id": "org_0123456789abcdef" }`. Anything else (no cookie, a wrong one, a signed-out one, a closed account): exactly `{ "signedIn": false }`.
- **Why the cookie arrives.** Home (`home.corporatetambola.com`), the games and the console are the same site (`corporatetambola.com`), so a browser sends a `SameSite=Lax` cookie on a credentialed `fetch` from Home to the console. The page calls `fetch("https://console.corporatetambola.com/api/me", { credentials: "include" })`. Nothing is copied to another host; the cookie stays on the console host only.
- **CORS.** `Access-Control-Allow-Origin` is the exact calling address (never `*`) and `Access-Control-Allow-Credentials: true` is sent only when the caller is `HOME_ORIGIN` (default `https://home.corporatetambola.com`) or one of the `GAME_ORIGINS` addresses, and only if it is an exact `https` origin on `corporatetambola.com` (a pages.dev, http, path or other-domain entry in the settings is ignored). Any other `Origin` gets 403 `{ "signedIn": false }` and no CORS header; the console's own page and a request with no `Origin` are served without CORS headers. `Vary: Origin, Cookie`, `Cache-Control: no-store`, `X-Robots-Tag: noindex`.
- **Safe on purpose.** GET (and the OPTIONS preflight) only; other methods get 405 and change nothing. No e-mail address, no e-mail hash (the join key the games match on) and no cookie value in the answer. No `Set-Cookie` (this route never sets or renews the cookie; `GET /auth/me` on the console still renews it). 1200 asks an hour per sign-in, then 429 (fixed hour window, the same `rate` table). The only write is the hourly "last seen" the session already does in `sessionOf`.
- **Name and ID.** The console stores no name, only the sealed e-mail, so `name` is made from the part of the e-mail before the `@` (`raajat.agarwal+x@...` gives "Raajat Agarwal"; letters only, at most 4 words and 40 characters; "Organizer" when nothing is left). `id` is `org_` plus the first 16 hex of `sha256("organizer|" + email hash)`: stable for the person, one way, and not the join key. Games that need the join key still get it only in a signed assertion from `POST /auth/assert`. If the owner wants a real name field later, it needs a sign-in form field and a migration; that is not in this release.

## 0.3.2 - 22 Nov 2026 (DEPLOYED 22 Nov 2026 16:12 IST, deployment 6c51d98b)

In plain words: the sign-in link in the e-mail no longer breaks if the page reloads itself once, and the saved copy of the pages keeps working in Firefox and older Safari.
### Fixed: H1, an automatic reload killed the one-time sign-in code (`public/signin.js`, `public/core/offline.js`)
- **What went wrong.** `signin.js` took the one-time code (`?t=`) out of the address bar at once and kept it only in memory. For a returning visitor who still held an older offline worker (0.2.2 or 0.3.0), the clean-up that runs on every page (`page-consent.js` then `removeWorker`) loaded the page once more to free it. The reload had no code in its address, so the button sent an empty code and showed "That link has run out" (untrue).
- **Now.** (1) The code stays in the address until the sign-in is proven: after the button, the page posts the code once, then asks the server `GET /auth/me`; only when that says signed in does it remove the code from the address and go to `/`. If the server does not confirm (a browser that refuses the cookie), the page says so in plain words and keeps the address. A reload at any time before that finds the code again and uses it once. (2) `removeWorker` never reloads a page that holds a one-time code or typed input (`holdsOneTimeInput`: sign-in, pay-link and pay pages, the owner page, any address with `t=`); the worker is still removed and its cache deleted, and the page is free on its next load. (3) One press sends the code once (a second press while it runs does nothing). (4) `public/sw.js` never keeps `/signin` or any address that carries `t=` (it already skipped `/signin.html`; the plain pay-link page without a code stays kept as before).
- Why `/auth/me` and not a cookie read: the sign-in cookie is `HttpOnly`, so no script can read it, neither `document.cookie` nor `cookieStore`. The server's answer works in every browser.
### Fixed: M1, browsers without `cookieStore` (Firefox, older Safari) (`public/sw.js`)
- **What went wrong.** Where a worker cannot read the cookie it relied on a flag in memory set by the page's `go`. Browsers stop and restart workers all the time; a restarted worker started at "no", so it neither wrote nor served the saved pages (offline load failed although the copy was there). Its install step also copied the shell without waiting for `go`.
- **Now.** The feature check is explicit (`answer()` returns yes, no, or unknown). Where it is unknown: install copies nothing and the worker stays until the page says `go`; on `go` it leaves a marker cache `console-shell-grant` and copies the shell once; after a restart the marker tells it the page said yes, so the saved pages are served again. The marker lives under the `console-shell-` prefix, so every decline (the page's `removeWorker`, or the worker's own `stop`) deletes it with the rest, and a `stop` that arrives while `go` is running wins. A privacy signal (GPC, Do Not Track) still means no first. Where `cookieStore` works, nothing changes: the cookie decides.
